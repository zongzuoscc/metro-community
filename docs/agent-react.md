# 社区 ReAct 执行说明

## 实际架构

主对话先走 Spring AI Alibaba Graph 的上下文压缩/记忆流程，再进入 ReAct 检索。
文章工具内部的标准检索组件、按需 HyDE 和跨库 RRF 说明见 [混合检索职责](agent-hybrid-retrieval.md)。
检索循环由 Spring AI Alibaba `ReactAgent` 驱动，使用标准工具调用消息与 `ToolCallback`，
不再由项目的 CALL/FINISH JSON 决策循环驱动。`NativeAgentRuntime` 负责接入业务权限、
冻结的 `PreparedUserAiChat`、调用预算和取消检查；这些是社区的业务约束，不由框架替代。

平台模型和用户自带模型均通过 Spring AI `OpenAiChatModel` 调用，平台 Embedding 通过
`OpenAiEmbeddingModel` 调用。保留的 HTTP 适配只传输字节；用户自定义端点维持公网地址校验和
固定 DNS，平台端点使用部署者配置与正常 DNS（不宣称平台同样固定 DNS）。两者均禁止代理和重定向，
模型请求编码、工具消息和上游 SSE 解析交给框架。依赖版本为 Alibaba 1.1.2.0、Spring AI 1.1.8。
用于 Agent 的平台/BYOK 模型需要支持 OpenAI 兼容的标准工具调用及流式响应；仅普通文本接口
连通不等于这两项能力可用。不支持时明确失败，不自动切回已删除的自研决策协议。

执行顺序：

1. 先查站内文章；用户开启联网时，即使站内有资料也执行一次联网查询。
2. 模型接收原始问题、近期对话/内部摘要、工具实际返回的证据与状态。
3. 模型返回标准 `tool_calls`；框架执行工具并将真实结果作为工具消息交给下一次模型调用。
4. 后端仍检查权限、参数、重复调用、运行权和预算；模型不提供 userId，不能自行扩大权限。
5. 模型不再请求工具，或资源/无进展边界触发后，结合已取得的资料生成最终答案。不要求输出、不记录内部思维链。
6. 最终回答走独立的正文生成调用；流式请求在生成中推送正文增量，完整结果经过引用校验和持久化完成事务后才发出成功终态。

不同查询可以重复调用同一工具。相同工具和规范化参数不会重复访问下游；
连续两次没有新增证据会停止，防止重复搜索空转。观察包含实际资料而非只有命中数量。
文章按稳定来源标识累积，网页按 URL 去重，并统一重编号，避免多次联网的 W1 指向不同网页。

## 边界与成本

- 只能查询文章、当前用户记忆、当前主对话历史、联网资料；模型没有写工具、用户身份参数、SQL 或 HTTP 执行接口。
- 临时对话不读取/写入持久记忆和历史；关闭记忆不能被模型绕过；关闭联网不能被模型绕过。
- 联网初次请求使用当前用户问题。后续联网动作必须经过独立的公共查询生成节点：它只接收当前问题与公开文章/网页，不接收私有历史、记忆或主决策提出的查询；公开观察中的内部查询也替换为当前问题。主决策不能直接把私有资料生成的查询发给搜索服务。用户当前问题仍会发送给联网服务，这不是自动识别所有敏感信息的 DLP 系统。
- 最大决策步数默认 6、工具尝试默认 8（包含初始检索）；兼容旧环境变量 METRO_AI_PLANNER_MAX_ROUNDS/MAX_TOOL_CALLS，部署硬上限为 16/24。
- 6 步指主循环决策次数，并非整轮模型调用总数；公共查询生成、HyDE、必要的上下文压缩与最终回答会额外调用模型，也受各自配额与整轮截止时间限制。
- 老 .env 若显式保留 2/4 会继续生效，应按需要改为 6/8。默认单次决策 PT6S，整轮还受总 deadline 和最终生成时间预留约束。
- Agent 的短窗口限额按模型调用计数，包含 ReAct 与 HyDE，不是用户问题数。默认由每分钟 8 调整至 24，避免一个合法多步请求自行耗尽旧限额；每天 100 次不变。达到配额会明确失败，不绕过计费保护。
- 决策输出最多 512 token；输入按真实序列化提示词估算预算。必需的问题和最新观察放不下时明确失败，不假装理解完整资料。
- 每个动作边界检查运行租约；取消后不再发起后续动作。已经发往供应商的请求可能仍执行/计费，不能承诺撤销。
- 记忆修改代际在压缩完成后冻结；后续模型请求发送前与返回后重新检查。期间删除或修改记忆会终止使用旧资料的回答，不把运行中已缓存的旧记忆继续交给下一次模型调用。
- 文章/历史/联网故障会作为 ERROR 观察，模型可以选择别的来源。记忆 Embedding/Milvus 故障与前次改造约定一致：明确失败，不退回词法记忆。
- 非法工具名、参数或模型响应仍明确失败，不悄悄变回旧手工计划。框架可能把节点异常转换为
  普通消息，因此业务适配记录本轮致命异常、阻断后续调用，并在图退出后重抛，不能把失败当作有效证据。

## 真正流式与业务 SSE 的分工

`OpenAiChatModel.stream()` 接收供应商持续发送的增量，业务层从生成中的答案 JSON 提取正文，
再通过现有 SSE 事件通道推送。不存在先等完整答案、再把完整字符串切片冒充模型流式的路径。
检索工具循环本身不是面向用户的正文；用户看到的是随后最终回答的增量，而不是模型的内部推理。

框架 1.1.8 对上游有两帧短缓冲，业务也有短批量合并，因此一个 SSE 事件不一定恰好等于一个 token。
验收标准是上游尚未生成完毕时前端已收到正文，而非要求每个 token 都独立发一个网络包。
不通过反射或同包子类访问框架内部方法来消除这一帧等待。

业务观察者通过公开 Reactor `publishOn` 与 `prefetch=1` 在共享虚拟线程调度器执行，
不在模型库内部的同步锁调用栈上等待数据库/Redis；读取和业务回调都不创建每请求线程池。
该边界是 Java 21 并发下的兼容适配，不是重新实现模型流式协议。

模型流式接口不负责社区的可靠投递：鉴权、事件游标回放、重连、取消、容量保护、
最终正文落库和成功终态仍由业务层负责。生成中展示的内容属于未完成结果，只有最终校验与
保存成功才确认完成；失败或取消不得被前端当作已成功保存的回答。

## 验证与部署

单元测试覆盖标准工具消息往返、实际观察、动态查询、重复工具、取消/权限、引用合并与输入预算，
以及嵌套 HyDE/Embedding 的冻结路由和实际发送前检查。迁移还覆盖合法 `content=null`、
框架异常传播、平台/BYOK 的流式取消和 usage 元数据；使用并发 HTTP 与 JFR 验证 Java 21 虚拟线程读取。
2026-09-10 最终选定后端套件 461 项通过，三个角色 JAR 构建成功；前端 148 项通过。
本机隔离测试验证首段早于上游结束、已启动上游的取消关闭、游标回放及保存正文一致性。
模拟上游下，扩容为 128 个执行槽、1024 个队列位置、1152 个 SSE 名额后，1000 临时/1000 持久
两批均全部成功，耗时约 27.0/28.1 秒；默认 200 人则接纳 96、容量拒绝 104。千人提交包含排队，
不是千路模型同时运行。最终 JFR 本次记录到 0 次 VirtualThreadPinned，不代表所有未来负载都无风险。
JDK 21 下执行：

```sh
./mvnw -q clean -Dtest='*Test,!*IntegrationTest,!*IT,!RecommendationMetricsTaskTest' test package
```

ReAct 本身不新增数据库表；一起交付的记忆改造仍需要先执行 [记忆升级步骤](agent-memory-compaction.md)。
构建/Mock 测试不代表真实模型任务成功率或高并发容量，部署后需用真实模型校准步数、延迟和成本。
本机隔离负载客户端见 [压测脚本说明](../scripts/agent-load/README.md)：使用真实 HTTP/MySQL/Redis，
上游为持续分段发送的模拟模型，明确区分默认容量拒绝、扩容后排队成功与实际模型并行数。
