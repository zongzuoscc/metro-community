# 文章详情阅读链路复测（2026-11-08）

## 建议写进简历的描述

基于 Redis Cache-Aside 与原子浏览量计数优化文章读取；在单机 128 并发连接、约 2 KB 正文的热点读取压测中，两轮各 60 秒吞吐均超 2.6 万次/秒，P99 ≤ 10 ms，累计完成 326 万次请求，未出现请求错误或正文校验失败。

这里的数字是本地实测，不是线上用户量、十万同时在线认证或 AI 模型吞吐。本轮没有性能优化前后的对照数据，因此不能写“性能提升若干倍”。

## 环境与边界

- 主机：Apple M5，10 核 CPU、16 GiB 内存，macOS；压测器、Java 和中间件位于同一台电脑。
- 后端：源码基线 `d0383e86de7447a92aeb288c218911221a501de2`，SDKMAN Java 21.0.11，Spring Boot 3.5.16，单个 Backend JVM，堆大小 512 MiB～1 GiB。
- 中间件：社区项目原有独立容器，MySQL 8.4.10、Redis 8.2；未使用 AIOps、五恒、mybot 的容器或数据。
- 数据：既有隔离库 `community_capacity_20260917`，1 万篇公开合成文章，ID 100001～110000，每篇正文 2016 个 UTF-8 字节；Redis 使用 DB 14，正常开发服务使用 DB 0。
- 测试端口：`127.0.0.1:18083`，接口 `GET /api/article/detail/{id}`；公开接口，不携带用户 JWT。包含 Spring Security 过滤链、JSON 序列化、真实 Redis 缓存查询与浏览量累加。
- 容量库保持既有 LEGACY 阅读模式，不伪称验证了 CUTOVER 模式的所有冷查询、权限、审核或索引链路。
- Hikari 最大连接数 10、最小空闲连接数 2；Tomcat `max-keep-alive-requests=100000`，HTTP/1.1 连接复用，pipelining=1。没有加载遗留的未跟踪 capacity-test 配置。
- 文章缓存 TTL 仍为业务默认 30 秒，不人为延长到覆盖整次测试；测量期间会发生正常过期和重新回填。
- 本轮不启动 Worker、不处理容量库的浏览量回写任务、不调用外部 AI API；不包含 CDN、TLS、网关、网络延迟或用户登录查询。
- 工具：Autocannon 9.0.0、Node.js v24.22.1。使用成熟压测工具，不通过自编并发循环替代测量器。

## 正式结果

热点场景从 1 万篇文章中轮转读取前 100 篇。15 秒、32 连接预热不计入正式成绩。随后按 128→256→128 的顺序测试，每档 60 秒，串行执行，不互相争用负载。

| 场景 | 并发连接 | 完成请求数 | 平均吞吐（次/秒） | 平均延迟 | P99 | 错误 / 超时 / 校验失败 | MySQL SELECT 增量 |
| --- | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| 热点 A | 128 | 1,691,143 | 28,186.40 | 4.05 ms | 9 ms | 0 / 0 / 0 | 4,585 |
| 热点加压 | 256 | 1,602,181 | 26,703.47 | 9.14 ms | 21 ms | 0 / 0 / 0 | 3,307 |
| 热点 B，重复验证 | 128 | 1,574,133 | 26,236.54 | 4.38 ms | 10 ms | 0 / 0 / 0 | 1,191 |

简历采用两次 128 连接结果的保守下界，不取第一次结果或某一秒的最高值。两轮完成数相加为 3,265,276。256 连接并未增加吞吐，反而抬高尾延迟，因此不能把连接数越大理解为性能越好。

原始测量会保留亚秒级尾部计时，Autocannon 的平均吞吐来自内部采样，因此不能简单用表中已取整的“60 秒”反算所有小数。精确时长和完整分位数见同目录的结果 JSON。

### 扩大候选范围的对照

另外把轮转候选文章从 100 篇扩大至 1 万篇，在 128 连接下测试。完成 735,178 次读取，Autocannon 采样平均为 12,253 次/秒，P99 为 34 ms，最大延迟为 4,815 ms；错误、超时、正文校验失败均为 0。含初始化的总测量时间为 64.87 秒，若按完成数除总时间，保守吞吐约 11,333 次/秒。

这一档要保留两个限制：大请求模板集的压测器初始化也占用同机 CPU；各连接从同一篇文章开始轮转，并不是全站均匀随机访问。测试结束时范围内只存在 5,745 条浏览量 key，不能宣传成已覆盖完全部 1 万篇。相应 MySQL SELECT 增量为 803,449，表明回源显著增加，与热点成绩不可互换。

这组数据说明访问分布和缓存工作集决定结果，不能只用缓存命中的最高成绩推导“任意文章都支持 2.6 万 QPS”。本次也没有量化缓存命中率或完成独立压测机的交叉验证。

## 如何确认不是“快速报错”或压测器虚高

1. 每个完成响应都验证 HTTP 200、业务 `code=200`、返回文章 ID 与请求对应、正文长度为 2016 字节。ID 按真实接口约定兼容 Long 字符串序列化。
2. 记录网络错误、超时、非 2xx、正文不符合预期的响应，任一出现即把该档标为失败，而不是计为有效成绩。
3. 对比服务端 Redis 的浏览量增量：三个正式档位分别为 1,691,271、1,602,437、1,574,261，均只比客户端完成数多出当档的并发连接数。这些是窗口结束时服务端已经执行、客户端停止前尚未完整接收的在途请求，不混入完成数。
4. 记录 MySQL 实例 `Com_select` 增量。该指标是全实例 SELECT 语句数，不是独立的业务请求数，也不能据此精确推导缓存命中率。本次没有其他业务负载；两次 128 档分别约 76、20 次 SELECT/秒，远低于 HTTP 阅读吞吐，符合缓存命中不回库的实现。
5. 初次试运行发现了 ID 类型误判，以及默认 Keep-Alive 换连接时的 Autocannon `ECONNRESET`。这轮已作废；修正校验、显式设置连接复用上限后，先通过小样本复核，再重新预热和正式测量。没有把失败的试运行包装成业务成功。

## 为什么这条链路能承担较高吞吐

缓存未命中时，业务按公开文章条件查 MySQL，补齐作者、标签后缓存快照；命中时直接从 Redis 返回，不再每次回 MySQL 校验正文。每次阅读仍真实执行 Redis Lua 浏览量自增和脏集合标记，并非关闭计数后的静态 JSON 接口。

写侧现有实现提交后失效缓存，结合事件补删和 TTL 控制陈旧窗口；加载占位与 Lua 条件回填避免迟到加载者覆盖已失效的缓存。这些机制不是本轮新加的。需要注意：未取得回填资格的请求仍会回源，不能把当前实现宣传成完整的热点 Singleflight 防击穿方案。

本轮只证明这个窄而完整的公开阅读链路在特定负载下的表现。搜索回库、长正文、缓存不可用、冷启动、私有用户数据、发布审核、Agent 整轮任务必须分别测量，不能套用此数字。

## 复现

在后端仓库根目录运行，要求容量库和上述合成数据已经存在；脚本不建库、不造数据、不删除数据。

```sh
source "$HOME/.sdkman/bin/sdkman-init.sh"
sdk use java 21.0.11-amzn
java -version
mvn -version
mvn -DskipTests package
docker start metro-community-mysql-1 metro-community-redis-1 metro-community-rabbitmq-1 metro-community-es-1
npm install --prefix target/resume-load --no-save --package-lock=false autocannon@9.0.0
node scripts/resume-load/start.cjs
curl --fail http://127.0.0.1:18083/actuator/health
node scripts/resume-load/read.cjs
# 把轮转候选集扩大至 1 万篇；不保证在测试窗口内覆盖完所有文章。
# 必须等待上一条命令完成，不能并行执行。
LOAD_SCENARIO=broad node scripts/resume-load/read.cjs
```

启动脚本只从社区容器现有环境读取凭据给测试 JVM，日志与结果不保存密码。本机测试采用 root 连接既有隔离库，是环境复用方案，不是生产权限建议。迁移到其他环境时应改用仅获授权访问压测库的专用账号。

默认结果保存在 `target/resume-load/results/`。启动脚本输出测试进程 PID，完成后只停止该 PID，并将本次启动的社区容器恢复至测试前状态。不要使用 `FLUSHALL`、清库或删除数据卷清理测试结果。
