# Metro Community 个性化推荐设计

## 目标与范围

首页当前的“推荐”流调用 `/api/article/feed`，按发布时间游标返回已发布文章。首页应改为明确分开的“推荐”和“最新”两个入口：“推荐”在数据不足时显示最新文章，数据达标后显示因登录用户而异的机器学习排序结果；“最新”始终按发布时间游标返回已发布文章。

第一版交付一个真实、可解释、可回滚的推荐闭环。它使用现有 MySQL、Redis、RabbitMQ 和 Elasticsearch，不依赖 AI Key、Embedding 服务或 mock 数据。

本轮不引入向量数据库、音视频推荐、独立推荐微服务、A/B 实验平台和用户显式“不感兴趣”按钮。学习排序的训练、模型导出、加载和推理属于本轮范围，但模型只有在真实数据满足双门槛后才参与推荐结果。

## 现有能力与取舍

- 详情页 `/api/article/{id}/similar` 保持不变。它使用 Elasticsearch `more_like_this` 按标题、摘要和正文找文章相似内容，继续承担内容相似召回。
- 首页 `/api/article/feed` 保持不变，作为“最新”页、未登录推荐页、推荐模块不可用和行为数据不足时的时间线来源。
- `/api/article/hot-feed` 和 `/api/article/follow-feed` 保持原有语义，分别作为全局热度与关注内容入口。
- 新的首页“推荐”只面向已登录用户。未登录用户继续使用现有时间线，并可通过热榜发现内容。登录用户也始终可以在“最新”页看到不受模型影响的时间线。

不采用“只按阅读、点赞、收藏总数重排”的方案，因为其结果仍几乎对所有用户相同，且会持续放大头部文章。

## 架构

```text
文章详情有效阅读、点赞、收藏、评论、关注作者
                         |
                         v
       MySQL recommendation_event_outbox
                         |
                         v
       RabbitMQ recommendation.event.queue
                         |
                         v
         MySQL user_article_event  <-  可审计行为事实
                         |
         +---------------+---------------+
         |                               |
         v                               v
Redis 标签偏好、作者亲和度          离线训练样本与特征快照
         |                               |
         v                               v
关注作者候选 + 标签候选 + ES 相似候选 + 热门新文候选
                         |
                         v
  双门槛检查 -> 规则冷启动排序 / 模型精排 -> 多样性重排
                         |
                         v
          GET /api/recommendations/feed?cursor=&size=
```

推荐代码先作为单体中的 `recommendation` 领域模块存在。模块对外只暴露事件发布、用户画像更新、训练模型读取和推荐流查询接口。RabbitMQ 消费者、Redis 缓存、MySQL 明细和模型文件都被封装在该模块中，后续可以按这个边界独立为推荐微服务，而无需改变首页 API。

## 行为采集

### 事件类型

| 事件 | 触发位置 | 初始兴趣权重 |
| --- | --- | ---: |
| `VIEW` | 前端详情页处于可见状态满 8 秒后上报 | 1 |
| `LIKE` | 文章点赞成功后由后端发布 | 4 |
| `COLLECT` | 收藏成功后由后端发布 | 8 |
| `COMMENT` | 评论成功后由后端发布 | 6 |
| `FOLLOW_AUTHOR` | 关注成功后由后端发布 | 10 |

`VIEW` 使用用户、文章、自然日作为幂等粒度，同一文章同一天只计一次有效阅读。其他事件使用业务动作的稳定去重键，消息重复投递不应重复累加画像。

### 持久化与异步边界

新增 `user_article_event` 表，保存用户、文章、事件类型、事件发生时间、去重键与来源。它是行为事实的唯一可恢复来源。

收藏、评论和关注在原业务事务内同时写入 `recommendation_event_outbox`，提交成功后由后台投递器发送到 `recommendation.event.queue`。点赞沿用现有异步落库链路，只在 `LikeConsumer` 真正插入文章点赞记录后，在同一事务写入 Outbox；取消点赞、评论点赞和重复点赞不产生推荐事实。

Outbox 投递使用 RabbitMQ publisher confirm。发送成功后标记完成，发送失败按退避时间继续重试，不把异常返回给已经完成的业务请求。若进程在 RabbitMQ 确认后、Outbox 标记完成前退出，消息可能重复发送，下游唯一去重键负责幂等处理。

消费者先以唯一去重键写入 MySQL，再根据 MySQL 行为事实幂等重建 Redis 画像。消费者失败由现有重试和死信队列处理，不影响点赞、收藏、评论或关注的主请求。

## 用户兴趣画像

Redis 保存两组按分数排序的近期兴趣：

- `recommendation:tag:{userId}`：标签兴趣分。
- `recommendation:author:{userId}`：作者亲和分。

事件根据文章标签和作者更新分数。权重按事件类型乘以时间衰减，最近 30 天的交互权重大于旧交互。Redis 画像有 TTL，并可由 `user_article_event` 重建。

## 数据门槛与机器学习排序

机器学习不在没有样本时参与推荐。推荐请求会同时检查以下门槛：

- 当前登录用户在最近 30 天有至少 20 条去重有效行为。
- 全站在最近 90 天有至少 500 条去重有效行为。

任一门槛未满足时，“推荐”页返回与“最新”页相同的时间线数据，并在响应中标记为冷启动，不伪造个性化原因。“最新”页无论门槛和模型状态如何，始终调用现有时间线接口。

两个门槛都满足后，系统仍先执行四路候选召回和资格过滤，再由轻量学习排序模型完成精排。第一版使用离线训练的 Logistic Regression：它读取 `user_article_event` 构造样本，以有效阅读、点赞、收藏、评论和关注后的内容互动作为正反馈，以未产生后续互动的已曝光内容作为负反馈。特征至少包括标签匹配、作者亲和、ES 相似度、热度、新鲜度、用户已读次数和候选来源。模型输出只替代规则精排分数，不替代召回、多样性和安全过滤。

训练作业只使用真实行为事实和已记录曝光，不使用 mock 数据。它按时间切分训练与验证数据，验证集指标未优于当前规则排序时不发布模型。模型以版本化 JSON 系数文件保存到本地受控目录，加载失败、特征缺失、模型过期或推理异常时立即回退规则排序；规则排序也无法提供足够候选时，再回退时间线。

## 候选召回与排序

### 候选召回

每次刷新最多产生 100 个去重候选：

- 20 篇关注作者的最新已发布文章。
- 40 篇高兴趣标签下的近期文章。
- 30 篇基于用户最近有效阅读或收藏文章的 Elasticsearch 相似文章。
- 20 篇热度与新鲜度兼顾的探索候选。

召回时过滤未发布、已删除、本人文章和当前推荐会话已经展示过的文章。用户行为很少时，标签候选和 ES 相似候选为空是正常情况，热度与新鲜度候选保证推荐不为空。

### 规则精排

冷启动和模型不可用时，初始得分由标签匹配、作者亲和、ES 相似来源、热度和新鲜度组成。已读文章被降权，短期重复作者和重复标签被降权。

模型可用且双门槛满足时，规则特征与模型特征保持同一套定义。模型给出点击或后续互动概率，规则分数保留小比例新鲜度加成，避免模型长期只推荐旧的高互动内容。

精排后执行多样性重排：连续三篇不得来自同一作者，同一标签在前十篇中不得超过四篇。推荐响应可携带简短 `reason`，例如“因为你收藏过 Redis 相关文章”或“来自你关注的作者”，方便调试和产品展示。

## 接口、缓存与降级

新增认证接口：

```text
GET /api/recommendations/feed?cursor=<opaque>&size=10
```

响应包含文章列表、下一页不透明游标和每篇文章的推荐原因。首次请求生成 10 分钟有效的推荐会话并在 Redis 保存排序后的文章 ID。分页只推进同一会话，避免滚动期间因热度变化而重复或跳过文章。

`recommendation.enabled` 只控制推荐结果，不停止行为与曝光采集；关闭排序后仍持续积累真实训练数据。推荐页关闭、双门槛未满足、Redis 不可用、模型不可用或候选不足时，服务端直接降级调用现有 `/api/article/feed` 对应的时间线查询。“最新”页始终调用该时间线。首页不应因推荐失败而空白。

## 实施阶段与验收

### 阶段一：行为事实

交付事件表、事务 Outbox、事件 DTO、RabbitMQ 队列与消费者，点赞、收藏、评论、关注、有效阅读均可产生幂等行为事件。首页结果不变。

验收：重复事件不重复入库；RabbitMQ 暂时不可用时 Outbox 保留并重试；消费者失败进入死信队列；业务主流程不受影响；文章点赞只有在 `like_record` 真正插入后才产生事件。

### 阶段二：画像与候选

交付 Redis 标签和作者画像、四路候选召回及冷启动候选。首页结果仍可通过开关保持原时间线。

验收：同一用户不同行为得到不同候选来源，未登录和行为不足用户的推荐页与最新页都得到非空时间线。

### 阶段三：曝光数据、训练与模型精排

交付推荐曝光事实、特征快照、时间切分的离线 Logistic Regression 训练任务、验证门槛、版本化模型文件和安全加载器。

验收：训练仅使用真实行为和曝光数据；未优于规则基线的模型不发布；模型推理只在双门槛满足时启用；加载或推理失败立即回退规则排序。

### 阶段四：排序接口与首页接入

交付双门槛、规则或模型精排、会话游标、原因字段、推荐开关，以及推荐页和最新页的前端接入。

验收：已读和本人文章不重复推荐，滚动分页稳定，关闭开关或模型不可用后推荐页立即恢复现有时间线，最新页始终保持时间线。

### 阶段五：质量与可观测性

交付推荐来源占比、曝光、有效阅读、点赞、收藏和评论的统计指标，以及异常和降级日志。

验收：能通过真实行为数据判断不同候选来源和排序规则是否有效。

## 测试与回滚

- 单元测试覆盖权重、时间衰减、去重、过滤、排序和多样性规则。
- 集成测试使用 Testcontainers 验证 MySQL、Redis、RabbitMQ 的 Outbox 投递、publisher confirm、事件消费和幂等性。
- API 测试覆盖认证、游标分页、冷启动、双门槛、Redis 失效、模型加载失败和推荐开关降级。
- 模型测试覆盖真实样本构造、时间切分、基线比较、模型版本校验和推理回退。
- 前端测试覆盖推荐原因展示、推荐和最新页的独立游标、游标追加和服务端降级响应。

所有新增表仅追加行为事实与曝光事实，不修改现有文章、点赞、收藏、评论或关注的历史数据。关闭 `recommendation.enabled` 即可停止推荐接口调用并让推荐页恢复时间线；行为明细和模型版本可保留供后续分析，不需要数据回滚。
