# Java 后端工程化加固设计

## 目标与边界

本阶段将 Metro Community 的后端从功能演示状态提升为可审计、可测试、可部署的 Java 服务。目标是消除已发现的安全和可靠性问题，稳定现有社区功能，并让项目经历能够经得起后端面试追问。

本阶段不新增 AI 能力，也不拆分独立微服务。AI 相关配置会保留安全的占位方式，AI API Key 缺失时服务应能启动，非 AI 功能和自动化测试不受影响。

## 安全与鉴权

- 使用 Spring Security 的无状态认证链路。JWT 从 `Authorization: Bearer <token>` 读取，并在过渡期兼容既有 `token` 请求头。
- 认证成功后将用户 ID 和角色写入 `SecurityContext`。业务代码从当前认证主体读取身份，不再在控制器中重复解析令牌或自行校验管理员角色。
- 仅开放认证、公开文章、标签等必要接口。上传、私信、收藏、互动、管理端和 AI 接口默认需要登录，管理端还要求管理员角色。
- JWT 密钥、允许跨域来源及 Token 有效期改为配置属性。生产环境通过环境变量传入，不在仓库中保存真实值。
- CORS 按环境读取来源白名单，不再允许任意来源携带凭据。

## 配置与运行环境

- 项目统一使用 Java 17，与 Spring Boot 3 的最低版本要求和 README 保持一致。
- 数据库、Redis、RabbitMQ、邮箱、OSS、AI 等配置全部从环境变量读取。提交 `application-example.yml` 和 `.env.example`，并忽略本地覆盖配置和 `.env` 文件。
- Docker Compose 使用变量化凭据，将中间件端口仅绑定到本机。Elasticsearch 继续作为开发环境依赖，生产安全配置不在本阶段假定为已完成。
- 删除重复的 Elasticsearch 依赖和未使用的 Fastjson 依赖，关闭默认 SQL 标准输出日志。

## 接口与业务规则

- 所有写接口 DTO 使用 Jakarta Bean Validation。校验必填字段、长度、邮箱格式、分页范围、枚举值与文章状态转换前置条件。
- 管理类接口使用明确 DTO 替代 `Map<String, Object>`，非法参数统一返回稳定的业务错误结构。
- 上传接口校验文件存在、大小、媒体类型和允许的扩展名，生成服务端文件名，不信任原始文件名。
- 统一异常处理，区分认证失败、权限不足、参数错误、资源不存在、冲突与服务器错误。响应不泄露异常堆栈或基础设施细节。
- 保留现有文章、评论、关注、点赞、收藏、举报及实时聊天的接口语义，避免破坏当前前端。

## 消息可靠性与可观测性

- RabbitMQ 消费异常不再被吞掉。为业务队列配置有限重试和死信队列，最终失败的消息保留原始负载与失败原因，便于排查和补偿。
- 消费者使用结构化日志记录消息 ID、业务 ID、队列和失败原因。AI 审核、ES 同步、互动计数和通知任务采用相同的失败处理约定。
- 本阶段不实现 Outbox。数据库提交与消息发布的原子一致性将在后续架构演进中作为独立工作处理，不能在 README 中宣称已完全解决双写问题。

## 测试、文档与交付

- 使用 MockMvc 和 Mockito 覆盖 JWT 鉴权、管理员越权、封禁账户、参数校验、上传策略、文章可见性和关键状态迁移。
- 增加测试环境配置，使测试不依赖真实数据库、消息队列、邮箱、对象存储或 AI 服务。
- 新增 GitHub Actions，在 Java 17 上执行 Maven 测试。
- 引入 OpenAPI 文档，作为前后端接口契约与本地演示入口。
- README 说明真实依赖、Java 版本、环境变量、Docker 启动、数据库初始化、接口文档、功能边界和已知限制。删除没有基准或测试支撑的性能数据与架构结论。

## 验收标准

1. `./mvnw test` 能在 Java 17 环境通过，且不需要真实外部中间件。
2. 公开、登录、普通用户、管理员四类请求均按接口权限策略得到正确结果。
3. 仓库、示例配置和 Docker 文件不含真实凭据或硬编码 JWT 密钥。
4. 非法输入、越权操作、消费失败和上传违规文件都有可预测的错误响应或可查询的失败记录。
5. README 的命令和配置可让新开发者完成本地启动，项目描述与实际实现相符。

## 后续顺序

完成本阶段后，优先推进 AI 应用加固，包括访问控制、限流、配额和成本控制、超时与降级、提示词注入防护、审核结果审计与真实 API 联调。随后再吸收 C 方案中的模块边界与 Outbox，是否拆成独立服务以实际负载、团队协作和部署需求为准。
